# OPL008: Asset loaded in hot path

| | |
|---|---|
| **Rule ID** | OPL008 |
| **Category** | Performance |
| **Default severity** | Info |
| **Enabled by default** | Yes |
| **Code fix** | No |
| **Since** | 1.6.0 |

## Cause

A hot path loads an asset:

- **`Resources.Load`, `Resources.Load<T>`, `Resources.LoadAsync` and `Resources.LoadAsync<T>`.**
  Unity caches the loaded object, so the second call does not read the disk again, but every call
  still looks the asset up by path, and `LoadAsync` allocates a new `ResourceRequest` each time.
- **Every `Addressables.Load*` method**: `LoadAssetAsync<T>`, `LoadAssetsAsync<T>`, `LoadSceneAsync`,
  `LoadResourceLocationsAsync`, `LoadContentCatalogAsync`. Each call allocates an operation and its
  async state, adds a reference count to the asset that only a matching `Addressables.Release` takes
  back, and hands back a new `AsyncOperationHandle`.
- **The `Load*` methods of an `AssetReference`** and its subclasses (`AssetReferenceT<T>`,
  `AssetReferenceGameObject`, `AssetReferenceSprite`, ...), such as `LoadAssetAsync<T>()`. Calling one a
  second time while the first load is still held throws, so in `Update` it is usually a bug outright.

None of these needs to run more than once per asset. The fix is the same for all of them: load in
`Awake` or `Start` and keep the result, or the handle, in a field.

The message names the API and the method it runs in:

```
'Resources.Load' loads an asset on every call inside the frequently-called method 'Update'. Load it once in Awake or Start and keep it in a field.
'Addressables.LoadAssetAsync' loads an asset on every call inside the frequently-called method 'Update'. Load it once in Awake or Start and keep the handle or its result in a field.
```

The rule is Info by default, like [OPL002](OPL002.md): a load in a hot path is sometimes deliberate
(behind input, or a cache miss), and the cost is lookup work and a handle rather than a per-frame array.
The Unity Console does not show Info diagnostics; raise the rule to a warning to see it there (see
[When to suppress](#when-to-suppress)).

Which methods count as hot paths follows [OPL001](OPL001.md#cause): the 18 built-in Unity messages on
a `MonoBehaviour`, plus whatever `.editorconfig` adds or excludes (see
[Configuration](OPL001.md#configuration)). Burst-compiled code is never reported. The rule runs only
when the compilation references `UnityEngine.Resources` or the Addressables package.

## Example

```csharp
using UnityEngine;
using UnityEngine.AddressableAssets;
using UnityEngine.ResourceManagement.AsyncOperations;

public class Spawner : MonoBehaviour
{
    public AssetReferenceGameObject enemy;

    GameObject _bullet;
    AsyncOperationHandle<GameObject> _enemyHandle;

    void Awake()
    {
        // Fine: loaded once
        _bullet = Resources.Load<GameObject>("Bullet");
        _enemyHandle = enemy.LoadAssetAsync();
    }

    void Update()
    {
        // OPL008: looked up by path every frame
        var bullet = Resources.Load<GameObject>("Bullet");

        // OPL008: a new operation and handle every frame, and a reference count that is never released
        var handle = Addressables.LoadAssetAsync<GameObject>("Enemy");
    }

    void OnDestroy()
    {
        if (_enemyHandle.IsValid()) Addressables.Release(_enemyHandle);
    }
}
```

## What is not reported, and why

- **`Resources.LoadAll`.** It returns an array, which [OPL003](OPL003.md) already reports.
- **`Addressables.InstantiateAsync` and `AssetReference.InstantiateAsync`.** They create a new
  instance on every call by design; how to reuse instances is [OPL001](OPL001.md)'s territory (pool
  them), not a caching question.
- **`Addressables.Release`, `Resources.UnloadAsset` and other non-loading members.**
- **A load assigned straight into a field** (`_prefab = Resources.Load<GameObject>("x");`), including
  a lazy `if (_prefab == null) _prefab = ...;`. The automatic
  [OPLS004 suppression](../suppressions.md#opls004-the-result-assigned-to-a-field) treats that as the
  caching the rule asks for. The other automatic suppressions (first frame, `#if UNITY_EDITOR`, a static
  latch) apply too.
- **Look-alike types.** Only `UnityEngine.Resources`, `UnityEngine.AddressableAssets.Addressables` and
  `UnityEngine.AddressableAssets.AssetReference` are matched, not a project's own `Resources` class.
- **Loads in methods called from the hot path.** As with OPL001, there is no call-graph analysis.

## How to fix

| Loading call | Fix |
| --- | --- |
| `Resources.Load<T>(path)` | Load in `Awake` or `Start` into a field, or better, reference the asset from a serialized field so it is not looked up by path at all. |
| `Resources.LoadAsync<T>(path)` | Start it once (from `Start` or a coroutine) and keep the `ResourceRequest` or its `asset`. |
| `Addressables.LoadAssetAsync<T>(key)` | Load in `Awake` or `Start`, keep the `AsyncOperationHandle<T>` in a field, use `handle.Result` once it completes, and call `Addressables.Release(handle)` in `OnDestroy`. |
| `assetReference.LoadAssetAsync<T>()` | The same: load once, keep the handle (or read `assetReference.Asset`), and call `assetReference.ReleaseAsset()` in `OnDestroy`. |
| A load that genuinely has to happen during play | Move it behind the event that needs it (a button handler, a level transition) rather than a per-frame check. |

## When to suppress

A load behind a condition that is rarely true (a cache miss, a one-off input event) runs seldom enough
not to matter. Suppress it there:

```csharp
#pragma warning disable OPL008 // Asset loaded in hot path
        var icon = Resources.Load<Sprite>(path);
#pragma warning restore OPL008
```

```ini
[*.cs]
# none | silent | suggestion | warning | error

```
