# OPL009: Component or object lookup in hot path

| | |
|---|---|
| **Rule ID** | OPL009 |
| **Category** | Performance |
| **Default severity** | Info |
| **Enabled by default** | Yes |
| **Code fix** | No |
| **Since** | 1.6.1 |

## Cause

A hot path looks up an object it could have looked up once:

- **`GetComponent<T>()`, `GetComponent(Type)`, `GetComponent(string)`, `TryGetComponent`,
  `GetComponentInChildren` and `GetComponentInParent`**, on `Component` or `GameObject`, called on this
  object or on one reached through its fields and properties: `GetComponent<Rigidbody>()`,
  `gameObject.GetComponent<T>()`, `transform.parent.GetComponent<T>()`, `_target.GetComponent<T>()`,
  `Player.Instance.GetComponent<T>()`. Each call searches the GameObject's component list (and, for
  `InChildren` and `InParent`, the hierarchy).
- **`GameObject.Find`, `GameObject.FindWithTag`, `GameObject.FindGameObjectWithTag`,
  `Object.FindObjectOfType`, `Object.FindFirstObjectByType` and `Object.FindAnyObjectByType`.** Each
  call walks the loaded scenes.

None of these allocates managed memory (OPL001 to OPL003 measure garbage, which is why they stay
quiet), but the lookup costs CPU time, and in `Update` it returns the same object every frame. The fix
is to look it up once in `Awake` or `Start` and keep it in a field.

The message names the API, what it does and the method it runs in:

```
'Component.GetComponent' looks up a component on every call inside the frequently-called method 'Update'. Get it once in Awake or Start and keep it in a field.
'GameObject.Find' searches the scene on every call inside the frequently-called method 'Update'. Find it once in Awake or Start and keep it in a field.
```

The rule is Info by default, like [OPL002](OPL002.md) and [OPL008](OPL008.md): a single
`GetComponent` is cheap, and the rule points at a habit rather than a per-frame allocation. The Unity
Console does not show Info diagnostics; raise the rule to a warning to see it there (see
[When to suppress](#when-to-suppress)).

Which methods count as hot paths follows [OPL001](OPL001.md#cause): the 18 built-in Unity messages on
a `MonoBehaviour`, plus whatever `.editorconfig` adds or excludes (see
[Configuration](OPL001.md#configuration)). Burst-compiled code is never reported.

## Example

```csharp
using UnityEngine;

public class Mover : MonoBehaviour
{
    Rigidbody _body;
    GameObject _player;

    void Awake()
    {
        // Fine: looked up once
        _body = GetComponent<Rigidbody>();
        _player = GameObject.Find("Player");
    }

    void Update()
    {
        // OPL009: the same component, looked up again every frame
        var body = GetComponent<Rigidbody>();

        // OPL009: a scene search every frame
        var player = GameObject.Find("Player");
    }

    void OnTriggerStay(Collider other)
    {
        // Not reported: a different object on every call, so there is nothing to cache
        if (other.TryGetComponent(out Health health)) health.Damage(1);
    }
}
```

## What is not reported, and why

- **A lookup on an object that changes from call to call.** `other.GetComponent<T>()` on the collider
  passed to `OnTriggerStay`, `hit.collider.GetComponent<T>()` on a raycast result, a lookup on a local,
  a method result or an array element: the object is different each time, so there is no single result
  to keep. Only receivers built from `this`, fields and properties (of classes, not structs such as
  `RaycastHit`) and static members are matched.
- **`GetComponents<T>()`, `GetComponentsInChildren<T>()`, `FindObjectsOfType<T>()`,
  `FindGameObjectsWithTag` and the other array-returning lookups.** They also allocate the array, and
  [OPL003](OPL003.md) reports them.
- **A lookup assigned straight into a field** (`_body = GetComponent<Rigidbody>();`), including a lazy
  `if (_body == null) _body = ...;`. The automatic
  [OPLS004 suppression](../suppressions.md#opls004-the-result-assigned-to-a-field) treats that as the
  caching the rule asks for. The other automatic suppressions (first frame, `#if UNITY_EDITOR`, a static
  latch) apply too.
- **`Camera.main`.** Unity has cached it internally since 2020.2, and this package targets 2021.3 and
  later.
- **Look-alike types.** Only `UnityEngine.Component`, `UnityEngine.GameObject` and
  `UnityEngine.Object` are matched, not a project's own `GetComponent` or `Find`.
- **Lookups in methods called from the hot path.** As with OPL001, there is no call-graph analysis.

## How to fix

| Lookup | Fix |
| --- | --- |
| `GetComponent<T>()`, `TryGetComponent`, `GetComponentInChildren<T>()`, `GetComponentInParent<T>()` | Look it up in `Awake` into a field. Better still, make it a serialized field and assign it in the Inspector, or add `[RequireComponent(typeof(T))]` so it is guaranteed to be there. |
| `GameObject.Find`, `FindWithTag`, `FindGameObjectWithTag` | Find it once in `Start` into a field, or have the object register itself with a manager (a static property set in its `OnEnable`). |
| `FindObjectOfType<T>()`, `FindFirstObjectByType<T>()`, `FindAnyObjectByType<T>()` | The same: find once, or keep a static instance (`public static T Instance { get; private set; }` set in `Awake`). |
| A lookup that has to follow a changing hierarchy | Refresh the cached field from the event that changes it (`OnTransformParentChanged`, a spawn callback) instead of every frame. |

## When to suppress

A lookup behind a rarely taken branch (a one-off input, a state change) runs seldom enough not to
matter. Suppress it there:

```csharp
#pragma warning disable OPL009 // Component or object lookup in hot path
        var target = GameObject.FindWithTag("Respawn");
#pragma warning restore OPL009
```

```ini
[*.cs]
# none | silent | suggestion | warning | error

```
