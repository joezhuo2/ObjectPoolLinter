# OPL007: Native container not disposed

| | |
|---|---|
| **Rule ID** | OPL007 |
| **Category** | Reliability |
| **Default severity** | Warning |
| **Enabled by default** | Yes |
| **Code fix** | No |
| **Since** | 1.6.0 |

## Cause

A native container is allocated with an allocator that Unity does not release by itself, and is not
disposed:

- held in a **local variable**, it is not disposed on every path out of the method, local function or
  accessor that allocates it;
- stored in a **field or auto-property** of the declaring type, no code in that type disposes it;
- **thrown away** as soon as it is made (`new NativeArray<int>(64, Allocator.TempJob);` as a
  statement).

A native container is any struct marked `[NativeContainer]`: `NativeArray<T>`, `NativeList<T>`,
`NativeHashMap<TKey, TValue>`, `NativeQueue<T>`, `NativeParallelHashMap<TKey, TValue>`,
`NativeReference<T>`, and those from other packages. Their memory lives outside the managed heap, so
the garbage collector never frees it. Unity logs the leak in the editor
(`A Native Collection has not been disposed, resulting in a memory leak`) and a player just keeps the
memory. Inside `Update`, a container that is not disposed leaks again every frame.

The message names the container, its allocator and what is missing:

```
'NativeArray<int>' allocated with Allocator.TempJob in 'Update' is never disposed. Call Dispose() on it, or declare it with 'using'.
'NativeArray<int>' allocated with Allocator.TempJob in 'Update' is not disposed on every path out of the method. Call Dispose() on it before each return, or declare it with 'using'.
'NativeArray<int>' allocated with Allocator.Persistent into '_buffer' is never disposed by 'Spawner'. Call Dispose() on it in OnDestroy, OnDisable or Dispose.
```

Unlike OPL001 to OPL003, the rule does not depend on hot paths or `MonoBehaviour`: a leak is reported
in any method of any type. It runs only when the compilation references Unity's
`NativeContainerAttribute` and `Allocator`.

### Which allocations are checked

Only an object creation (`new NativeArray<T>(...)`, or `new(...)` with a native container as the
target type) whose allocator argument is a constant:

| Allocator | Checked |
| --- | --- |
| `Allocator.TempJob`, `Allocator.Persistent`, and any other value | Yes |
| `Allocator.Temp` | No: Unity frees Temp memory at the end of the frame (or of the job) |
| `Allocator.None`, `Allocator.Invalid` | No: nothing is allocated |
| A variable, parameter or field (`new NativeArray<int>(n, _allocator)`) | No: the rule cannot tell which allocator it holds |

An allocator passed as an `AllocatorManager.AllocatorHandle` (the `NativeList<T>` and
`NativeHashMap<TKey, TValue>` constructors) is recognized through its conversion from `Allocator`.

### Every path out of the method

For a local, the rule follows the method's control flow from the allocation to every way out of it:
each `return`, the end of the method, and a loop turning back to the allocation, which replaces the
old container without disposing it. On every one of those paths the container must be:

- disposed: `Dispose()`, or `Dispose(JobHandle)` to free it once a job completes;
- disposed by a `finally` block the path runs through;
- declared with `using` (`using var buffer = ...;` or `using (var buffer = ...) { }`);
- or handed on (see below), after which it is someone else's to dispose.

A path that ends in `throw` does not count: the exception is the bug to fix there.

## Example

```csharp
using Unity.Collections;
using Unity.Jobs;
using UnityEngine;

public class Spawner : MonoBehaviour
{
    NativeArray<Vector3> _positions;
    public int count;

    void Awake()
    {
        // OPL007 unless something in Spawner disposes it (see OnDestroy below)
        _positions = new NativeArray<Vector3>(1024, Allocator.Persistent);
    }

    void Update()
    {
        // OPL007: the early return skips Dispose, so this leaks whenever count is 0
        var hits = new NativeArray<int>(count, Allocator.TempJob);
        if (count == 0) return;

        var handle = new CountJob { Hits = hits }.Schedule();
        handle.Complete();
        hits.Dispose();

        // Fine: using disposes it at the end of the method
        using var scratch = new NativeArray<int>(count, Allocator.TempJob);

        // Fine: Temp memory is freed by Unity at the end of the frame
        var temp = new NativeArray<int>(count, Allocator.Temp);
    }

    void OnDestroy()
    {
        if (_positions.IsCreated) _positions.Dispose();
    }
}
```

## What is not reported, and why

- **Containers handed on.** A local that is returned, assigned to anything (a field, another local, a
  job's field), passed by `ref` or `out`, passed to a method or constructor declared in the project's
  own source (`Release(buffer)`), or read by a lambda or local function becomes some other code's to
  dispose. A container passed to a method from a compiled assembly (a Unity API such as
  `RaycastCommand.ScheduleBatch`) stays the caller's and is still checked.
- **Containers created straight into another object.** `new MoveJob { Positions = new NativeArray<float3>(...) }`
  and `job.Positions = new NativeArray<float3>(...)` are not followed; a field marked
  `[DeallocateOnJobCompletion]` is disposed by the job system.
- **Containers created by a method** (`CollectionHelper.CreateNativeArray`, `mesh.AcquireReadOnlyMeshData()`,
  `ToNativeArray(allocator)`). Only `new` expressions are checked.
- **Allocations inside a lambda or anonymous method**, whose control flow is not followed.
- **Fields disposed from another type.** A field counts as disposed when any code in its declaring
  type, across every partial declaration, calls `Dispose` on it or passes it to the project's own code;
  a manager disposing another component's field is not seen.

A field is checked for a `Dispose` call anywhere in its type, not for one on every path: when a field
may be disposed twice or not at all depends on the order Unity calls `OnEnable`, `OnDisable` and
`OnDestroy`, which the rule does not model.

## How to fix

| Situation | Fix |
| --- | --- |
| A local used within one method | `using var buffer = new NativeArray<T>(...);`, or `Dispose()` before each `return` |
| A local that must survive an exception | `try { ... } finally { buffer.Dispose(); }` |
| A container a job reads | `handle.Complete(); buffer.Dispose();`, or `buffer.Dispose(handle)` to free it once the job completes |
| A container kept across frames | Allocate it once with `Allocator.Persistent` in `Awake`/`OnEnable`, dispose it in `OnDestroy`/`OnDisable`, and reuse it every frame instead of allocating |
| Scratch memory used only within the frame, on the main thread or inside a job | `Allocator.Temp`, which needs no `Dispose` |

A `TempJob` container is meant to live at most four frames; allocating one per frame is normal for
job-driven code, as long as each one is disposed.

## When to suppress

A container that intentionally lives for the whole run, such as a static lookup table built once, may
be left undisposed; the operating system reclaims it when the process exits. The editor still reports
the leak on each domain reload.

```csharp
#pragma warning disable OPL007 // Native container not disposed
    static NativeArray<int> s_table = new NativeArray<int>(256, Allocator.Persistent);
#pragma warning restore OPL007
```

```ini
[*.cs]
dotnet_diagnostic.OPL007.severity = none
```
